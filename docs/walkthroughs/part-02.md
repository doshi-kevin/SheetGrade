# Part 2 walkthrough: the workbook reader

This replaces the earlier chat explanation of Part 2, which was a log of what got done, not something teachable. Terms are defined the first time they appear; see `docs/GLOSSARY.md` for the full list.

## 1. What we built, in plain English

Before this project can compare a student's spreadsheet to the teacher's answer key, the code has to actually open the Excel file and turn it into something the rest of the program can work with: every filled-in box (cell), its value, whether it's a formula, what color it's shaded, whether it's merged with neighboring boxes. Without this piece, nothing downstream has anything to work on — there's nothing to detect regions in, nothing to align, nothing to grade. This is the front door of the whole pipeline.

## 2. Tiering what's actually in Part 2

- **Tier 1 — understand this deeply:** the dependency graph. See section 3.
- **Tier 2 — purpose only:** the tests. We wrote a handful of specific checks ("does the title cell read back correctly?") plus one golden snapshot test — a saved copy of everything the reader produced, so any future accidental change to its output shows up as a visible difference instead of slipping through unnoticed.
- **Tier 3 — mine, not yours:** the exact way a library called `openpyxl` represents merged cells internally, or which object type it hands back for a date versus a currency number. That's trivia about one specific library, not project understanding.

## 3. The one idea worth understanding: the dependency graph

Take a real cell from our test file, `tests/fixtures/keys/sample_key.xlsx`. Cell `F3` contains the formula `=SUM(B3:E3)`. That formula reads four other cells — B3, C3, D3, E3 — to produce its own answer. A **dependency graph** is just a record of that fact: "F3 depends on B3 through E3."

For this file, the graph we built looks like this:

| Cell | Formula | Depends on |
|---|---|---|
| F3 | `=SUM(B3:E3)` | B3:E3 |
| F4 | `=SUM(B4:E4)` | B4:E4 |
| B5 | `=B3-B4` | B3, B4 |
| C5 | `=C3-C4` | C3, C4 |
| D5, E5, F5 | same pattern | one column over each |

**Why this matters.** This project's whole second bet (see the Project section of `CLAUDE.md`) is: grade the calculation, not just the final number. Say a student's Profit row (`B5`) is wrong. There are two very different reasons that could be true:

1. Their formula itself is wrong (they added instead of subtracting).
2. Their formula is correct, but a number it depends on — say their Revenue cell, B3 — is wrong.

Without a dependency graph, a grader only sees "B5 is wrong" and would take points off wherever a wrong number shows up — including B5, even though the *method* in B5 was fine. With the graph, we can walk backward from a wrong cell to find where the error actually started, confirm the formula that used it was correct given its (wrong) input, and take points off exactly once, at the source.

That's Part 19 (scoring with carry-through) — this graph is the map it will walk. Part 2's whole job was to build that map; using it comes later.

## 4. The decision: formula as text, or formula as structure?

Right now a formula cell just stores its raw text: `"=SUM(B3:E3)"`, character for character. There was a second option: turn that text into a **parsed structure** instead — break `=SUM(B3:E3)` into its actual pieces ("this is the SUM function, applied to the range B3 through E3") rather than leaving it as one string of characters. That structured version is called an **AST**, short for abstract syntax tree — a tree-shaped breakdown of an expression into how its parts combine.

Text is enough for the dependency graph above — we only need to spot cell references, which a simple text pattern-match handles. It's not enough for a harder question coming up soon: is `=A1+A2+A3` the *same calculation* as `=SUM(A1:A3)`? Different text, same actual computation — a student who wrote either one did the same correct thing, and shouldn't be marked wrong for phrasing it differently. You can't answer that from raw text; you need the structured version to compare what the formulas actually *compute*, not how they happened to be typed.

We didn't build the structured version now, on purpose. The code that turns formula text into that tree — a **recursive descent parser** — is one of the five pieces of this project you build yourself, by hand, without AI help. It's scheduled right before Part 14, which is where formula-equivalence checking gets used for real. Building it now would mean writing something you'd then rewrite a version of later — wasted effort on both sides. So: text now, structure later, when you build the parser.

## 5. One honest problem we haven't solved

Every formula cell we read back from `sample_key.xlsx` came back with no cached value — the number Excel would normally have stored the last time it calculated that formula. That's because this test file was generated by a Python library, not opened and saved by real Excel, and only real Excel actually performs the calculation. Real student submissions will have a cached value. But we can't always trust it — Excel's cached value can go stale if a file is edited without recalculating — and if we ever need to grade a formula for a cell Excel never calculated at all, we'll need our own way to compute the answer. That's not solved yet. Flagging it here so it isn't forgotten by the time it matters.
